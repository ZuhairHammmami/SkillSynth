# ADR-014: Referential-Integrity Policy (FK validation, rename-uniqueness, cycle guards, restricted deletes)

## Status
Accepted

## Context
The ERD declared cascade/set-null behavior on every foreign key, but the API layer trusted it blindly — and that trust failed in four ways. Deletes cascaded silently: removing a skill or job role wiped dependent rows with no warning and no census, so an admin could destroy a hand-built path graph with one click. Renames could duplicate: `POST` checked name uniqueness but `PUT` did not, and the check that did exist was case-sensitive, so "Python" and "python" coexisted as separate skills. Bad references leaked 500s: a create/update carrying an unknown `category_id`, `skill_id`, or `prerequisite_ids` entry sailed past validation into SQLAlchemy, surfacing as an unhandled IntegrityError. And nothing prevented cycles: a category could be its own ancestor and a skill its own (transitive) prerequisite, which would break the topological sort at the heart of path generation.

## Decision
1. **FK validation at the service layer → 400 naming the bad reference** (`services/catalog_integrity.py`). `ensure_category_exists` guards `skills.category_id` writes, `ensure_resource_skill_exists` guards `resources.skill_id`, and `ensure_skills_exist` batch-checks id lists (`prerequisite_ids`, job-role `skill_ids`), naming every missing id in one message. Bad references die as 400 before any INSERT.
2. **Rename-uniqueness, case-insensitive, on updates → 409.** `update_skill` / `update_category` / `update_job_role` compare the incoming name/title case-insensitively against all other rows; a collision returns "already exists", which the shared mapper (`routers/error_mapping.py`) maps to 409.
3. **Cycle guards → 400.** Categories: self-parent is rejected and parent assignments walk the `parent_id` ancestor chain — re-reaching the edited row proves the edge would close a loop. Skills: self-prerequisite is rejected and candidate prereqs are DFS-walked over `repo.get_prerequisite_graph`; reaching the edited skill again proves a cycle. The DAG invariant for topological sorting is therefore enforced at write time, not hoped for at read time.
4. **Restricted deletes on skills, categories, job_roles → 409 with a census payload unless `?force=true`.** While dependents exist, DELETE returns
   ```json
   {"detail": {"message": "Cannot delete skill: it is referenced by other records. Retry with ?force=true to delete anyway.",
               "dependents": {"path_steps": 3, "resources": 2, "assessments": 1}}}
   ```
   (`dependents` = per-table counts from `repositories/integrity_repository.py`). With `?force=true` the ERD contract applies exactly: `skill_prerequisites` edges (both directions) and `path_steps` cascade, `resources`/`assessments` set null, category deletion SET NULLs its skills' `category_id`, and job-role mappings cascade. User deletion stays forced-by-design (personal data erasure).
5. **Centralized IntegrityError → 409** (`main.py`). Any constraint breach that slips past service validation (e.g., a duplicate `job_role_skills` junction row) hits one exception handler returning a generic 409 — never a 500 — and the request-scoped session rolls back when `get_db` closes.

The shared status contract (`error_mapping.status_for_error`): structured dict payloads (restricted-delete censuses) always mean 409; "*not found*" means 404; conflict markers ("already exists", "in use", "demote") mean 409; everything else (unknown references, cycles) means 400.

## Consequences
- The admin app gained a force-delete flow: the 409 census drives a confirm dialog showing what will be removed before `?force=true` is sent.
- Wire compatibility: duplicate-name responses differ by verb — POST duplicates keep their legacy 400 while PUT renames return the new 409 (pinned by `tests/test_integrity.py::test_duplicate_natural_keys_map_to_client_errors`).
- No delete can silently destroy referencing rows, and no write can produce a reference the database would reject or a cycle the topo-sort couldn't order.
- Service-layer checks run extra queries per write; acceptable at this scale and far cheaper than opaque DB errors.
- The IntegrityError handler is a safety net, not a design surface: new code must still validate up front.

## Options Considered
1. Rely on DB-level FKs alone — rejected: SQLite enforces them only under PRAGMA, the error strings are driver-specific, and they say nothing about renames or cycles.
2. Always-cascade deletes with no census — rejected: silent data loss was precisely the bug.
3. Block deletes outright — rejected: admins need a remediation path; the census + `?force=true` gives informed consent instead.
4. Return the raw IntegrityError text in the 409 safety net — rejected: leaks schema internals; a generic message plus rollback suffices.
